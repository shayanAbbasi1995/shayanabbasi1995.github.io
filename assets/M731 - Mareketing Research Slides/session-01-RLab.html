Purpose and how to use this document

The slide deck (session-01.qmd) live-codes a short version of this material in class. This document is the full, self-contained teaching companion: it covers everything you need — RStudio, Quarto, and R basics through a first exploratory data analysis (EDA) — in one place, with real output and an interpretation after every step. Work through it at your own pace, ideally by typing the code yourself rather than copy-pasting, in a fresh .qmd file rendered in RStudio.

By the end you should be able to: read a CSV into R, inspect and understand what you loaded, derive new variables, find and fix common data-quality problems, summarise data numerically, and visualise it with ggplot2 — the same five moves you will repeat, with fancier statistics layered on top, in every remaining session of this course.

Dataset. data/maritime_transactions.csv is instructor-simulated: six months of Maritime Roast subscription orders, generated by Sources/slides/data-raw/generate_datasets.R with a fixed seed so it is exactly reproducible. It deliberately contains a handful of realistic data-quality problems — inconsistent category labels, duplicate rows, a few bad amounts, and legitimate missing values — so that the “cleaning data” section below has real work to do rather than a clean toy table with nothing to fix.

Working in RStudio

You do not need to memorise this section — it is a reference for your first few weeks.

  • Source pane (top-left). Where you write and edit .qmd and .R files. Run the current line with Ctrl+Enter (Cmd+Return on Mac); run an entire code chunk with the green “play” arrow in its top-right corner, or Ctrl+Shift+Enter.
  • Console (bottom-left). Where R actually evaluates code and prints results when you are working interactively, outside of a chunk.
  • Environment pane (top-right). Lists every object currently in memory — every variable and data frame you have created. If a data frame you expect isn’t there, you probably haven’t run the chunk that creates it yet.
  • Files / Plots / Packages / Help pane (bottom-right). Lets you browse the project folder, view the most recent plot, manage installed packages, and read function documentation (?read_csv opens the help page here).
  • Render (Ctrl+Shift+K, or the “Render” button above the source pane) knits the whole .qmd file top to bottom into HTML, running every chunk in order in a fresh R session. If something only works because of a variable you created earlier and later deleted, Render will catch it even though “Run all chunks” might not.
Note

If RStudio’s Visual editor mode ever refuses to open a .qmd file with an error like “Error parsing code chunks out of document,” the usual cause is a code-fence character sequence appearing somewhere it shouldn’t (for example, demonstrating chunk syntax inside another code block). Switch to Source mode, fix the fence, and Visual mode will work again.

Working in Quarto

A .qmd file has three parts: a YAML header between --- lines (controls the output format and document metadata), prose (ordinary Markdown), and code chunks (fenced with ```{r} / ```, containing R code that actually runs when the document renders). The “Anatomy of a .qmd file” slide in session-01.qmd shows this visually if you want the picture version.

Inside a chunk, #| lines set chunk options — settings for that specific chunk. The ones you’ll use constantly this term:

Option Effect
label: A short, unique name for the chunk (used in cross-references and error messages)
echo: Show the R code itself in the rendered output? (true/false)
eval: Actually run the code? (false is useful for showing syntax you don’t want executed)
warning: / message: Suppress R’s warning/message text from cluttering the output
fig-width: / fig-height: Size, in inches, of any plot the chunk produces
fig-cap: Caption text under a figure

This document sets sensible defaults once, in the YAML header (execute: block above), so individual chunks below don’t repeat echo/eval/warning/message every time — only when a chunk needs to deviate from the default.

R Basics: Data Types

Before touching a real dataset, it’s worth seeing R’s basic data types in isolation, because every column you load later will be one of these.

a_number    <- 15.99                          # numeric (double)
a_count     <- 3L                             # integer
a_word      <- "Standard"                     # character
a_flag      <- TRUE                           # logical
a_date      <- as.Date("2026-01-01")          # Date
a_category  <- factor("Signature",
                      levels = c("Standard", "Signature", "Discovery"))

class(a_number); class(a_count); class(a_word); class(a_flag); class(a_date); class(a_category)

Interpretation. class() tells you what R thinks a value is, which determines what you’re allowed to do with it — you can take the mean() of numbers, but not of characters; you can compare Dates with < and > to find “which order came first,” but comparing plain character strings that happen to look like dates (“2026-01-01” vs “2026-1-1”) can silently give the wrong answer. Getting column types right when you read data in is therefore not a formality — it’s the first data-quality check.

Making (Deriving) Variables

Raw columns are rarely the variables you actually want to analyse. mutate() adds new columns computed from existing ones.

tx <- tx |>
  mutate(
    order_weekday   = wday(order_date, label = TRUE, abbr = FALSE),
    is_weekend      = order_weekday %in% c("Saturday", "Sunday"),
    order_size      = case_when(
      quantity == 1 ~ "Single bag",
      quantity == 2 ~ "Two bags",
      quantity >= 3 ~ "Three or more"
    ),
    delivery_speed  = case_when(
      delivery_days <= 3               ~ "Fast (<=3 days)",
      delivery_days <= 7               ~ "Standard (4-7 days)",
      delivery_days > 7                ~ "Slow (>7 days)",
      TRUE                             ~ NA_character_
    ),
    # a check, not just a convenience variable: does the recorded amount
    # match what price x quantity x discount + shipping implies? Note:
    # deliberately NOT coalescing missing shipping_cost to 0 -- if we
    # don't know the shipping fee, we can't verify the total, and the
    # check should honestly say "unknown" (NA) rather than guess.
    expected_amount = round(unit_price * quantity * (1 - discount_pct) + shipping_cost, 2),
    amount_gap      = round(amount - expected_amount, 2)
  )

tx |> select(order_id, order_weekday, is_weekend, order_size, delivery_speed, amount, expected_amount, amount_gap) |> head(5)
# A tibble: 5 × 8
  order_id order_weekday is_weekend order_size    delivery_speed      amount
     <dbl> <ord>         <lgl>      <chr>         <chr>                <dbl>
1        1 Sunday        TRUE       Two bags      Standard (4-7 days)   58.4
2        2 Wednesday     FALSE      Three or more Standard (4-7 days)   67.1
3        3 Friday        FALSE      Single bag    Slow (>7 days)        17.0
4        4 Monday        FALSE      Two bags      Slow (>7 days)        35.2
5        5 Friday        FALSE      Single bag    Standard (4-7 days)   14.1
# ℹ 2 more variables: expected_amount <dbl>, amount_gap <dbl>

Interpretation. order_weekday and is_weekend come from lubridate::wday(), loaded automatically with tidyverse. case_when() is mutate()’s tool for “if this, then that, else…” bucketing — cleaner to read than nested ifelse() once you have more than two cases. expected_amount and amount_gap are the more important pattern here: recompute a value two independent ways and compare them. Most rows should show amount_gap at or near zero; rows where it doesn’t are exactly the data-entry errors the next section goes looking for. Rows with a missing shipping_cost get an NA amount_gap — that’s correct behaviour, not a bug: with an unknown input, R (correctly) refuses to guess whether the total is right, rather than silently assuming shipping was free. Substituting a 0 there (e.g. via coalesce()) would have manufactured 100+ false “errors” out of orders that were simply missing one unrelated field — a good example of how a cleaning check can itself introduce bias if you’re not careful about what a missing value actually means.

Cleaning Data

Cleaning is not “delete anything that looks wrong.” It’s: find every issue, understand why it’s there, and decide — row by row or issue by issue — whether to fix it, flag it, or leave it and document why. This section works through four issue types found in tx.

Missing values

tx |>
  summarise(across(everything(), ~ sum(is.na(.)))) |>
  pivot_longer(everything(), names_to = "column", values_to = "n_missing") |>
  filter(n_missing > 0) |>
  arrange(desc(n_missing))
# A tibble: 7 × 2
  column              n_missing
  <chr>                   <int>
1 satisfaction_rating      9782
2 delivery_days             451
3 delivery_speed            451
4 shipping_cost             301
5 expected_amount           301
6 amount_gap                301
7 subscriber_id              15

Interpretation. Three columns carry missing values, and each has a different reason — this matters, because the right response depends on the reason, not just the count:

  • satisfaction_rating is missing for most rows because only survey-responding customers have one. This is not a data error — it is a real, structural non-response pattern, and dropping those rows before any analysis involving satisfaction would silently bias the sample toward survey-responders. The correct move is usually to keep the NAs, use na.rm = TRUE in summaries, and report the response rate alongside the results.
  • delivery_days is missing for orders not yet delivered as of the data pull — also structural, not an error, but worth footnoting in any delivery-time analysis.
  • shipping_cost missing values look like a genuine sync glitch between the order system and the shipping system — a smaller number of rows, no obvious pattern, worth flagging to whoever owns that data pipeline rather than silently imputing a number.
  • subscriber_id missing on a handful of rows represents guest checkouts never linked to an account — expected in an e-commerce system, not an error, but it does mean those rows can’t be used in any subscriber-level (as opposed to order-level) analysis.

Inconsistent category labels

tx |> count(tier, sort = TRUE)
# A tibble: 6 × 2
  tier          n
  <chr>     <int>
1 Standard   8325
2 Signature  4541
3 Discovery  2137
4 SIGNATURE    16
5 discovery    11
6 standard     10

Interpretation. tier should have exactly three values, but whitespace and capitalization inconsistencies (” standard”, “SIGNATURE”, “discovery”, etc.) have split it into more. This is one of the most common real-world data problems — the same underlying category entered inconsistently by different systems or people. Fix with str_squish() (trims and collapses whitespace) and str_to_title() (standardises capitalisation):

tx <- tx |>
  mutate(tier = str_to_title(str_squish(tier)))

tx |> count(tier, sort = TRUE)
# A tibble: 3 × 2
  tier          n
  <chr>     <int>
1 Standard   8335
2 Signature  4557
3 Discovery  2148

Interpretation. Three clean tier levels, as expected. Always re-run the check (count()) immediately after a cleaning step — never assume the fix worked.

Interpretation. duplicated() flags rows that are an exact repeat of an earlier row (every column identical) — consistent with a sync or export glitch that wrote the same order twice, not with two genuinely different orders that happen to share some values. distinct() keeps one copy of each. As with any cleaning step, report the before/after row counts explicitly rather than silently changing the data.

Outliers and data-entry errors

ggplot(tx, aes(x = tier, y = amount, fill = tier)) +
  geom_boxplot(outlier.color = "firebrick", show.legend = FALSE) +
  labs(x = "Tier", y = "Order amount ($)") +
  theme_minimal()

Interpretation. A handful of points sit far outside the whiskers — some negative, some implausibly large. Negative order amounts and amounts several multiples of a normal order are not “unusually generous customers”; they’re the signature of a data-entry problem (a refund miscoded as a charge, a quantity typo). Confirm with the amount_gap check built earlier, then flag rather than silently drop:

tx <- tx |>
  mutate(
    amount_flag = case_when(
      amount < 0                    ~ "Negative amount",
      abs(amount_gap) > 5           ~ "Amount does not match price x qty",
      TRUE                          ~ NA_character_
    )
  )

Visualizing Data with ggplot2

Every ggplot2 plot follows the same recipe: ggplot(data, aes(...)) sets up what maps to where, then one or more geom_*() layers say how to draw it.

Distribution: histogram

ggplot(tx_clean, aes(x = amount)) +
  geom_histogram(binwidth = 2, fill = "#7A003C", color = "white") +
  labs(x = "Order amount ($)", y = "Number of orders") +

Interpretation. The right-skew flagged by summary() is visible directly: most orders cluster in a normal range, with a thinning tail of larger multi-bag or Discovery-tier orders.

ggplot(tx_clean, aes(x = tier, y = amount, fill = tier)) +

Putting It Together

Maritime Roast’s Standard tier generates the most orders but the lowest average order value and the highest churn-flag rate; Discovery is the opposite on all three counts. Combined with the acquisition channel table, this suggests two different customer motions worth separate marketing treatment — a high-volume, price-sensitive Standard segment and a smaller, higher-value, more loyal Discovery segment — rather than one blended “average subscriber” strategy. This is the kind of one-paragraph, decision-relevant conclusion every EDA in this course should end with: not just tables and plots, but what they imply for a specific business choice.

Take-Away

The pattern in every section above is the same five-step loop:

  1. Read the data and check what you actually got (glimpse(), spec()).
  2. Derive the variables you actually need (mutate(), case_when()).
  3. Clean, deliberately and visibly — find issues, understand them, decide, and document what you did (count(), duplicated(), boxplots, flag-don’t-silently-delete).
  4. Describe numerically (summary(), group_by() + summarise()).
  5. Visualise to see what the numbers alone hide (ggplot2).

If you can run this loop from memory on a new dataset, you’re ready for Week 2.
